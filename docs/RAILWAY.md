# ДомПульс на Railway

Источник: `pistaha/DomPuls`, ветка `main`, корень репозитория. Backend запускается через `npm start` на Node.js 24.x. Секреты задаются в Railway Variables; `.env` не загружается в GitHub или через браузер.

## Текущая готовность

Код подготовлен и проверен локально. Рабочий production-деплой пока заблокирован отсутствием согласованных зон, username бота и MAX ID администраторов. Токен команда добавляет самостоятельно в Railway Variables, не передавая его Codex. Публичный HTTPS-адрес ещё не создан и не проверен.

На момент проверки в Chrome: workspace `Yarik's Projects`, Trial, 0 проектов; при выборе GitHub Repository показано `No repositories found` и `Configure GitHub App`. Платный план не выбран, webhook не регистрировался.

## Данные здания

Исходный `config/buildings.example.json` содержит условные корпуса и этажи. Его нельзя превращать в production простой заменой `synthetic`.

В `config/buildings.production.template.json` оставлен пустой массив `buildings`. Для заполнения нужны подтверждённые командой данные:

| Поле | Что заполнить |
| --- | --- |
| `buildings[].id` | Стабильный уникальный ID дома, латиница/цифры/`_`/`-`, до 80 символов |
| `buildings[].name` | Согласованное название или адрес дома |
| `buildings[].units[]` | Реальные корпуса/подъезды: у каждого `id` и `name` |
| `buildings[].zones[].id` | Стабильный уникальный в доме ID общей зоны |
| `unitId` | ID корпуса/подъезда из `units` |
| `floor` | Фактический этаж, целое число |
| `name` | Название общей зоны |
| `places` | Непустой список фактических общих мест в этой зоне |

Нужно также согласовать, какие общие места объединяются в одну зону для подсчёта обращений. У каждого корпуса должна быть хотя бы одна зона. Личные комнаты/квартиры не добавляйте. `synthetic: false` означает, что заполненные данные проверены командой. Пустая, некорректная или синтетическая конфигурация останавливает production до открытия HTTP-порта.

Скопируйте шаблон в локальный игнорируемый `config/buildings.pilot.json`, заполните его и вставьте весь JSON в Railway Variable `BUILDINGS_JSON`. В Railway не добавляйте `BUILDINGS_FILE` одновременно с этой переменной. Сам файл для этого способа не требуется коммитить или загружать на Volume.

## Переменные сервиса

Здесь `ДОМЕН` — точное имя, полученное в Railway → Settings → Networking → Generate Domain. Замените его в трёх URL, без кавычек. Это таблица настройки, а не готовый `.env` с секретами.

| Railway Variable | Значение |
| --- | --- |
| `NODE_ENV` | `production` |
| `RAILPACK_NODE_VERSION` | `24` (также закреплён через `engines.node=24.x` и `.nvmrc`) |
| `HOST` | `0.0.0.0` |
| `PORT` | `8080`; укажите этот же target port при создании домена |
| `DATA_DIR` | `/data` — обязательно вместе с подключённым Volume |
| `PUBLIC_URL` | `https://ДОМЕН` без завершающего `/` |
| `MINI_APP_URL` | `https://ДОМЕН/` |
| `MAX_WEBHOOK_URL` | `https://ДОМЕН/webhook/max` |
| `MAX_BOT_TOKEN` | Уже выданный токен; команда вводит его непосредственно в Railway и скрывает/seals значение |
| `MAX_BOT_USERNAME` | Username уже выданного бота, без `@` |
| `MAX_ADMIN_IDS` | Числовые MAX ID администраторов через запятую; не username и не ID бота |
| `USER_HASH_SECRET` | Случайный секрет минимум 32 символа; сохраните для следующих деплоев и восстановления БД |
| `MAX_WEBHOOK_SECRET` | Другой случайный секрет, 32–256 символов `A–Z`, `a–z`, `0–9`, `_`, `-` |
| `BUILDINGS_JSON` | JSON с согласованными реальными зонами, описанный выше |

Для каждого из двух новых секретов можно отдельно выполнить локально `openssl rand -hex 32` и перенести результат в Railway Variables. Это генерирует новые значения и не читает токен бота. Не храните секреты в документации, исходниках или истории Git. `USER_HASH_SECRET` нельзя менять при каждом деплое: от него зависит связь пользователя с прежними заявками.

Railway также умеет автоматически назначать `PORT`; backend всегда читает значение из окружения. Явный `8080` выбран здесь, чтобы target port и health check были однозначны. `NODE_EXTRA_CA_CERTS` нужен только при фактической необходимости дополнительного доверенного CA; не отключайте проверку TLS.

## Настройка в Chrome

1. Подготовьте данные из таблицы выше. В текущем Trial не выбирайте платный тариф без отдельного согласования.
2. Railway Dashboard → **New → GitHub Repository**. Если список пуст, нажмите **Configure GitHub App**, выберите аккаунт `pistaha` и дайте Railway доступ только к `DomPuls`, затем вернитесь и нажмите **Refresh**. Этот доступ настраивает владелец аккаунта GitHub.
3. Выберите `pistaha/DomPuls`. В Settings → Source проверьте ветку **main** и корень проекта. Если доступен шаг **Add Variables / Configure**, заполните настройки до Deploy. Если Railway начал первый запуск автоматически, он может завершиться ошибкой до заполнения production-настроек; не переключайте его в development ради зелёного статуса.
4. В настройках сборки выберите **Railpack**, Build Command: `npm test && npm run build`, Start Command: `npm start`. Node должен быть **24.x**. Не используйте `npm run dev`, `serve` или статический `dist/public` как backend.
5. На схеме проекта вызовите меню правой кнопкой → создание **Volume** (или через `⌘K`), подключите его к сервису ДомПульс, Mount Path: **`/data`**. Установите `DATA_DIR=/data`. Одна переменная без Volume не обеспечивает сохранение базы. Если появляется требование оплатить тариф, остановитесь до согласования.
6. Settings → Networking / Public Networking → **Generate Domain**, target port **8080**. Внесите полученный домен в `PUBLIC_URL`, `MINI_APP_URL`, `MAX_WEBHOOK_URL` в точных форматах выше. HTTPS обслуживает Railway; в Node не нужны файлы сертификата для входящего соединения.
7. Variables → внесите остальные переменные. `MAX_BOT_TOKEN` вводит команда самостоятельно. Проверьте имена переменных, не раскрывая значения секретов.
8. Settings → Deploy → Healthcheck Path: **`/health`**, timeout **60 секунд**. Оставьте **1 replica**, один регион; отключите Serverless/App Sleeping для стабильного приёма событий. Pre-deploy Command оставьте пустым. Не помещайте туда регистрацию webhook или инициализацию SQLite.
9. Примените изменения и запустите Deploy/Redeploy. Дождитесь успешной сборки и прохождения health check. База создаётся при старте в `/data/pilot.sqlite`, файлы WAL/SHM находятся рядом на том же диске. Volume монтируется на этапе запуска, не сборки.

Настройки задаются в интерфейсе Railway. Старый `railway.json` здесь не добавлен: актуальная документация Railway помечает Config as Code как устаревающий механизм для legacy-сервисов. `npm start`, версия Node и поведение приложения закреплены в репозитории.

## Проверка после деплоя

Пока домен и production-настройки не готовы, эти проверки выполнить нельзя. После успешного запуска:

```sh
curl --fail --show-error --silent https://ДОМЕН/health
curl --fail --show-error --silent https://ДОМЕН/api/config
curl --output /dev/null --silent --write-out '%{http_code}\n' https://ДОМЕН/.env
```

Ожидается: `/health` → HTTP 200 и `{"ok":true}`; `/api/config` → `development:false`, `synthetic:false` и согласованные зоны; `/.env` → 404. Откройте `/` в браузере: должен загрузиться пилот, вход по тестовым аккаунтам недоступен. Health check читает реальную SQLite и возвращает 503 без технических подробностей, если база недоступна. Он не проверяет токен запросом к MAX и не подтверждает регистрацию webhook. Railway использует эту проверку при деплое, а не как постоянный мониторинг.

После подключения к MAX создайте согласованную тестовую заявку, выполните Restart сервиса, заново откройте приложение из MAX и убедитесь, что заявка сохранилась. После рестарта сессии требуют нового входа. Volume допускает краткий простой при замене экземпляра; масштабирование на несколько экземпляров с текущей SQLite не предусмотрено. Настройте резервные копии Volume, не копируйте только основной `.sqlite` из работающей WAL-базы.

## Что остаётся для MAX

1. Получить username и права настройки **уже выданного** бота, числовые MAX ID администраторов.
2. После проверки HTTPS указать `MINI_APP_URL` в настройках этого бота и включить кнопку открытия. Если доступ принадлежит организаторам, передать им URL и username; токен для этого пересылать не нужно.
3. Только после отдельного подтверждения зарегистрировать webhook командой `npm run bot:register` в окружении сервиса. Она здесь не запускалась и не включена в build/start/pre-deploy.
4. Проверить подписанный вход в реальном клиенте MAX, права администратора, три обращения от разных участников и общий статус. Домен и локальные тесты сами по себе не подтверждают работоспособность внутри MAX.
