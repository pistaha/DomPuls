# ДомПульс — пилот MAX и отдельное демо

ДомПульс собирает похожие обращения об отсутствии холодной воды. В пилоте ИТМО **три разных участника с совпадающей категорией проблемы и выбранной категорией места за 20 минут** создают запись «Похожие обращения / возможный общий инцидент». Это сигнал для последующей проверки, а не подтверждение общей причины или аварии. Проверка и связь с УК находятся вне сервиса.

Интерфейс остаётся обычным HTML/CSS/JavaScript. Сохранены стиль, макет телефона и демонстрационный чат исходного прототипа. Добавлены один Node.js-сервер и SQLite — без сторонних npm-зависимостей и сборщика интерфейса.

**У команды уже есть токен бота, выданный для хакатона.** Используйте его через `MAX_BOT_TOKEN`; создавать нового бота или регистрироваться в MAX для бизнеса для этого проекта не требуется. Живое подключение пока не проверено: предстоит настроить окружение, HTTPS-хостинг и открытие приложения у выданного бота. Локально полностью работают серверные заявки, общая база, объединение, права, статусы и отдельный сценарий защиты.

**Railway:** пошаговая настройка сервиса, Volume `/data`, переменных и проверки HTTPS — в [RAILWAY.md](RAILWAY.md). Для пилота ИТМО готов `../config/buildings.itmo.json`: категории места без неподтверждённых номеров блоков, этажей и инженерных схем.

## 1. Локальный запуск без MAX

Понадобится **Node.js 24.x**. В терминале VS Code из папки проекта:

```sh
node --version
cp -n .env.example .env
npm run dev
```

Команда `cp -n` сохраняет уже существующий `.env`. Если файл уже есть, добавьте недостающие настройки по `.env.example`, не перезаписывая выданный токен.

Откройте [http://localhost:3000](http://localhost:3000). Установка npm-пакетов не нужна. Остановка — Ctrl+C.

Если появляется «Порт 3000 уже занят», проверьте другой терминал: приложение может уже работать. Остановите предыдущий запуск через Ctrl+C и повторите `npm run dev`. На macOS команда `lsof -nP -iTCP:3000 -sTCP:LISTEN` покажет процесс, занимающий порт. Если порт нужен другому приложению, укажите в `.env` свободный `PORT`, например `3001`, и соответствующий `PUBLIC_URL=http://localhost:3001`.

`npm run dev` явно устанавливает `NODE_ENV=development`. Такой сервер слушает только loopback. На странице выберите «Участник 1», «Участник 2», «Участник 3» или «Администратор разработки» и нажмите «Войти локально». Для смены участника используйте «Выйти». Эти аккаунты **не являются подтверждёнными пользователями MAX**.

Заявки этого режима действительно записываются в общую SQLite-базу `data/development.sqlite`. Они помечены в интерфейсе как тестовые. Серверный пилот использует другой файл — `data/pilot.sqlite`; проверка внутри БД дополнительно запрещает использовать файл другого режима.

Пользуйтесь именно адресом из `PUBLIC_URL` (`localhost` и `127.0.0.1` — разные origin). Если меняете порт, поменяйте одновременно `PORT` и `PUBLIC_URL`.

Открытие `index.html` напрямую или через прежний `python3 -m http.server` **больше не запускает пилот**: для общих заявок нужен backend. При недоступности API экран объяснит, как запустить Node. Старый автономный сценарий сохранён в `demo.html`; его можно открыть как файл, но при запуске через сервер доступ к `/demo` требует прав администратора.

### Запуск через Docker

Нужны Docker Engine/Desktop и Docker Compose. В репозитории есть Node 24 Dockerfile для production (`npm start`) и Compose-сценарий для безопасной локальной проверки без токена MAX. Compose явно игнорирует локальный `.env`; Docker build тоже исключает `.env`, базы и локальные данные.

```sh
docker compose --env-file /dev/null up --build -d
curl --fail --show-error http://localhost:3000/health
docker compose --env-file /dev/null ps
```

Откройте `http://localhost:3000`. Войти можно тестовыми ролями **Участник 1–3** и **Администратор разработки**. Создайте обращения в одинаковой категории места от трёх участников, чтобы проверить появление похожих обращений и смену статуса. Эти тестовые аккаунты не являются пользователями MAX; Docker Compose не отправляет запросы MAX и не выполняет регистрацию webhook.

Если порт 3000 уже занят, задайте, например, `DOMPULSE_HTTP_PORT=3001` перед каждой командой `docker compose` выше и откройте `http://localhost:3001`.

SQLite в этом режиме хранится в `/data/development.sqlite` в именованном Volume `dompulse-data`. Остановить и запустить заново, сохранив базу:

```sh
docker compose --env-file /dev/null down
docker compose --env-file /dev/null up -d
```

Не добавляйте `-v` к `down`, если хотите сохранить базу. Опубликованный порт привязан только к `127.0.0.1`; `CONTAINER_DEV=1` разрешает development-серверу принимать forwarded-запросы только в этом локальном Docker-сценарии. Production Dockerfile запускает `npm start`, слушает `0.0.0.0:$PORT` и использует `/data/pilot.sqlite`; production требует переменных раздела 3 и постоянного Volume, подключённого на `/data`. Перед запуском entrypoint чинит владельца только `/data`, поскольку Railway монтирует Volume как root, и затем запускает приложение от непривилегированного пользователя `node`.

### HTTP-контракт и данные для проверки

Публичные продуктовые методы и вебхук описаны в [../openapi.yaml](../openapi.yaml) (OpenAPI 3.1). `/health` документирован отдельно как проверка готовности. `../DATA-API.yaml` содержит воспроизводимые read-only проверки health, открытой конфигурации, состояния сессии и запрета чтения данных без входа. Его структура следует публичному примеру API Judge с `schemaVersion: "1.0"`, блоками `solution`/`api` и списком `checks` ([пример](https://gitverse.ru/stasnorman/ex-task)). `baseUrl` уже указывает на домен проекта; перед отправкой организаторам замените placeholder `teamId` на выданный команде ID и проверьте, что Railway домен отвечает после деплоя.

Для ручной проверки локального Docker существуют только три тестовых жителя (`dev-1`, `dev-2`, `dev-3`) и локальный администратор (`dev-admin`); UI выбирает их через список входа. Это доступы development-режима, не реальные MAX-учётные данные. Production-доступ требует подписанного входа MAX, MAX ID из `MAX_BUILDING_ACCESS` для конкретного дома и, для администратора, MAX ID из `MAX_ADMIN_IDS`. Подпись MAX не подтверждает право проживания. Перед пилотом внесите соответствия только по списку, переданному уполномоченной стороной; без него сервер оставляет заявки закрытыми.

### Лимиты запросов и история

Polling `GET /api/state` обновляет только открытые агрегаты и текущие похожие обращения; личная история и список инцидентов загружаются отдельными страницами по 20 записей. В ответе — курсор по `(created_at, id)`; интерфейс добавляет следующие записи кнопкой **Показать ещё**. Максимальный размер страницы — 50. Для сортировки используются индексы `(user_key, building_id, created_at, id)` и `(building_id, created_at, id)`.

Лимиты независимы по действию: один проверенный аккаунт может опрашивать состояние до 120 раз в минуту, получать страницу истории до 60 раз, отправлять до 10 заявок и менять статус до 30 раз в минуту. Вход ограничен 60 попытками с одного сетевого peer за минуту; публичные конфигурация и чтение сессии — по 120 запросов с peer. При проверке peer используется адрес TCP-соединения; `X-Forwarded-For` не считается достоверным и не используется. На Railway авторизованные запросы ограничиваются по HMAC-псевдониму MAX пользователя, поэтому общий адрес прокси не складывает polling жильцов.

Пример JSON заявки и последовательность проверки с тремя локальными ролями — в [../test-data/README.md](../test-data/README.md). Файл не содержит заселённых пользователей или сведений о планировке.

Интеграции: SQLite и API заявок работают локально по-настоящему; MAX Bridge и HMAC-проверка реализованы для production, но реальный вход на Railway здесь не подтверждён. Тесты подменяют исходящий HTTP-вызов Bot API и используют локальный вход, поэтому это mock, а не проверка бота MAX. Связи с УК, автоматической диагностики и уведомлений нет.

## 2. Демо за минуту

1. На локальном пилоте войдите как **Администратор разработки**.
2. Откройте **Управление → Открыть демо для защиты**.
3. На отдельной странице нажмите **Запустить демо**. Видны этапы «1/3 → 2/3 → 3/3» и один общий инцидент. Если уже есть тестовые сообщения, добавляются недостающие жители.
4. Выберите статус **Мастер вызван**, затем в переключателе **Демо-режим** выберите **Житель** — тот же статус виден на главной.
5. Для повторного показа: **Администратор → Сбросить демо → Да, сбросить тестовые данные**. Ссылка **К пилоту** возвращает в серверное приложение.

Демо использует отдельный ключ localStorage `dompulse-demo-v1`. Его JavaScript **не вызывает API пилотных заявок**. Сброс удаляет только демонстрационные записи браузера. Обычный участник не видит вход в демо; сервер запрещает ему `/demo`, `/app.js` и `/model.js`. Скачанный ранее автономный демо-файл тоже не имеет доступа к реальным данным.

Для показа именно общей базы: создайте по заявке от трёх локальных участников в одинаковой зоне. Первому будет видно «1 из 3», второму — «2 из 3», третьему — общий инцидент. Войдите администратором и измените статус. Вернитесь к участнику или откройте его сессию в другом браузере. Обновления подгружаются каждые 5 секунд, когда пользователь не заполняет форму/список; есть кнопка ↻.

## 3. Настройка `.env`

`.env`, базы, `data/`, `dist/` и локальная конфигурация реальных зон исключены из Git. Сервер раздаёт файлы по явному списку: секреты, исходники backend и БД недоступны по HTTP.

### Уже выданный токен хакатона

1. Откройте локальный `.env` в редакторе VS Code. В `.env.example` строка `MAX_BOT_TOKEN=` намеренно оставлена пустой.
2. Вставьте выданный токен после `MAX_BOT_TOKEN=` **только в `.env`** и сохраните файл. Не вставляйте его в README, исходники, команду терминала или чат. Существующий `.env` с токеном не нужно пересоздавать.
3. Укажите `MAX_BOT_USERNAME` выданного бота без `@`. Если username или права настройки URL не предоставлены вместе с токеном, уточните их у организаторов хакатона — новый бот не нужен.
4. Перезапустите backend. `npm run dev`, `npm start` и `npm run bot:register` читают `.env` штатным механизмом Node. На хостинге можно задать `MAX_BOT_TOKEN` как секретную переменную окружения; переменные процесса имеют приоритет над `.env`.

Один `MAX_BOT_TOKEN` используется сервером для проверки подписи MAX и авторизации запросов бота. Клиенту токен не передаётся, в URL и журналы запросов не выводится. Само добавление токена не регистрирует webhook и не публикует мини-приложение. Для проверки интерфейса без MAX оставьте `NODE_ENV=development`; для реальных участников настройте production по разделу 5.

| Переменная | Назначение |
| --- | --- |
| `NODE_ENV` | `development` для локальной проверки; **`production` для настоящих участников** |
| `PORT`, `HOST` | Локально `3000`, `127.0.0.1`; в production HOST по умолчанию `0.0.0.0`. На Railway явно задайте `HOST=0.0.0.0` |
| `PUBLIC_URL` | В production ваш HTTPS origin, например `https://dompulse.example`, без пути и завершающего `/` |
| `MINI_APP_URL` | Тот же origin с `/`: `https://dompulse.example/` — URL для кабинета MAX |
| `MAX_BOT_TOKEN` | Уже выданный команде токен хакатонного бота; только на сервере |
| `MAX_BOT_USERNAME` | Публичный username бота без `@`, используется в кнопке `open_app` |
| `MAX_ADMIN_IDS` | Числовые MAX `user.id` аккаунтов команды через запятую; это не username и не ID бота |
| `MAX_BUILDING_ACCESS` | JSON-карта MAX ID → список `building-id`, выданная уполномоченной стороной; без соответствия сервер запрещает читать и отправлять обращения в дом |
| `USER_HASH_SECRET` | Случайный секрет, минимум 32 символа, для необратимого псевдонима пользователя в БД |
| `MAX_WEBHOOK_SECRET` | Отдельный случайный секрет, 32–256 символов `A–Z`, `a–z`, `0–9`, `_`, `-` |
| `MAX_WEBHOOK_URL` | `https://ваш-домен/webhook/max` |
| `DATA_DIR` | Путь к постоянному диску, по умолчанию `./data` |
| `BUILDINGS_FILE` | JSON с согласованными домами и зонами |
| `BUILDINGS_JSON` | Альтернатива файлу: тот же JSON целиком в переменной Railway. Не задавайте одновременно с `BUILDINGS_FILE` |
| `NODE_EXTRA_CA_CERTS` | При необходимости абсолютный путь к официальному доверенному PEM bundle для Node; TLS-проверка остаётся включённой |

На macOS два секрета генерируйте **отдельными** запусками команды: каждый результат попадёт в буфер обмена без печати в терминал; вставляйте его прямо в соответствующее поле Railway Variables (для локальной настройки — в `.env`):

```sh
openssl rand -hex 32 | pbcopy
```

Не присылайте токен в чат, не кладите его в HTML/JS и не коммитьте `.env`. `USER_HASH_SECRET` нужно сохранять вместе с резервной копией БД: его смена меняет псевдонимы и связь с прежними личными заявками. После смены токена/списка администраторов перезапустите сервер, чтобы сбросить существующие сессии.

При запуске без явного `NODE_ENV=development` обход проверки MAX отсутствует. `npm start` без production-настроек завершится с понятной ошибкой. Команду `npm run dev` нельзя использовать для публикации.

## 4. Пилот ИТМО без неизвестной планировки

Для Railway задайте `BUILDINGS_FILE=config/buildings.itmo.json`; `BUILDINGS_JSON` оставьте незаданным. Конфигурация использует режим `reported-place`. Он не требует `units`, `zones`, номера блока или этажа.

Доступны только категории «душ/туалет в блоке», «прачечная, 1-й этаж», «столовая», «учебная комната», «другое», «не знаю». Этаж столовой и учебной комнаты не задан. Публичные сведения и границы точности описаны в [ITMO_PILOT.md](ITMO_PILOT.md).

Группировка: дом + категория проблемы + выбранная категория места + окно 20 минут. Совпадение категории места не означает один физический блок, помещение, стояк или причину. Старый нерешённый инцидент не поглощает новую волну вне своего временного окна. Три участника — продуктовый порог, а не число жильцов блока.

В API историческое поле `zoneId` в этом режиме хранит ID категории места из `places`, а не номер или идентификатор физической зоны. Сервер проверяет соответствие ID и названия. Неизвестная детализация отсутствует, не заменяется фиктивными числами или строками.

`config/buildings.example.json` и отдельное браузерное демо сохраняют **условную** структуру только для локальной разработки. Для будущего режима с физическими зонами нужны согласованные реальные корпус/подъезд, этажи и границы общих зон. Они не обязательны для текущего пилота. Пустой `buildings.production.template.json` сам по себе не является конфигурацией для запуска.

При смене конфигурации с непустой БД сервер сохранит данные и остановится до явной миграции. Не удаляйте реальные заявки ради смены структуры.

## 5. Backend, бот и подключение HTTPS к MAX

Код подготовлен по официальной документации MAX, проверенной 26.09.2026. Бот работает **в том же Node-процессе**, отдельного сервиса и long polling нет.

1. Используйте **уже выданного хакатонного бота**. Заполните `MAX_BOT_TOKEN` и `MAX_BOT_USERNAME` по разделу 3. Если у команды есть только токен, согласуйте изменение URL мини-приложения с организаторами или владельцем этого бота; создавать другого бота не нужно.
2. Получите числовые MAX ID администраторов команды и внесите их в `MAX_ADMIN_IDS`. Только ID из подписанного запуска, проверенного сервером, сравнивается с этим списком. Клиентская роль/переданный отдельно `userId` прав не дают.
3. Разместите репозиторий на сервере с Node 24.x и постоянным диском для SQLite. Настройте HTTPS reverse proxy на порту **443** с доверенным сертификатом: `/`, `/api/*`, `/health`, `/demo` и `/webhook/max` направляются на один backend. На собственном сервере можно явно задать `HOST=127.0.0.1`; на Railway нужен `HOST=0.0.0.0`. Не раздавайте весь репозиторий как статическую папку. Не публикуйте development-сервер.
4. Заполните production-переменные и выберите конфигурацию пилота ИТМО. Проверьте, что `NODE_ENV=production`, затем запустите:

   ```sh
   npm start
   ```

   В production обязательны токен, секреты, администраторы, HTTPS URL, webhook URL и username. Запускайте один экземпляр backend; для постоянной работы используйте менеджер процессов вашего хостинга. Не размещайте SQLite на временном диске serverless-функции.

5. В настройках **уже выданного бота** укажите `MINI_APP_URL` и включите кнопку открытия. Если права на эти настройки принадлежат организаторам, передайте им только публичный HTTPS URL приложения и username бота; токен пересылать для этого не нужно. При доступе команды к кабинету путь: **Чат-боты → выданный бот → ⋮ → Настройки**. См. [официальную инструкцию подключения мини-приложения](https://dev.max.ru/docs/webapps/introduction).
6. Когда HTTPS уже доступен, **самостоятельно** зарегистрируйте webhook:

   ```sh
   npm run bot:register
   ```

   Команда отправляет подписку на `bot_started` и `message_created`; она не запускается автоматически при старте приложения. Endpoint проверяет `X-Max-Bot-Api-Secret`, прежде чем обрабатывать событие. Бот отвечает на начало диалога и `/start` кнопкой **Открыть ДомПульс** (`open_app`, `web_app` = username бота). Остальные сообщения в чате не создают заявки. См. [webhook](https://dev.max.ru/docs-api/methods/POST/subscriptions) и [клавиатуру](https://dev.max.ru/docs-api/use-cases/sending-messages/keyboard).
7. Откройте бота в MAX, нажмите Старт и кнопку приложения. Проверьте вход обычного участника и администратора, три заявки из разных аккаунтов, общий статус и сохранение после перезапуска backend.

Текущая документация MAX указывает API-домен `platform-api2.max.ru`; токен передаётся заголовком `Authorization`, не в URL. Если Node сообщает об ошибке доверия сертификату, настройте доверенный CA через `NODE_EXTRA_CA_CERTS` по официальным инструкциям MAX/хостинга. **Не отключайте проверку TLS**. См. [отправку сообщений](https://dev.max.ru/docs-api/methods/POST/messages).

Команда регистрации и реальная отправка сообщений здесь не выполнялись. Локальные тесты бота используют имитацию HTTP-ответа API.

## 6. Проверка входа и приватность

При запуске из MAX загружается официальный [MAX Bridge](https://dev.max.ru/docs/webapps/bridge). Он даёт `window.WebApp.initData`; в обычном браузере загрузка SDK не нужна. `initDataUnsafe` для аутентификации не используется. В MAX интерфейс убирает рамку телефона и занимает webview.

Сервер реализует [официальный алгоритм проверки](https://dev.max.ru/docs/webapps/validation): однократное URL-декодирование, уникальные ключи и один `hash`, сортировка, HMAC-SHA256 с ключом `WebAppData`, затем подпись строки данных и сравнение за постоянное время. Проверяется `auth_date`: максимум 1 час, допустимое опережение часов — 30 секунд. Время заявки задаёт сервер.

После проверки сохраняется только HMAC-псевдоним ID пользователя. ФИО, фото, телефон, username, IP из initData и сами стартовые данные не записываются в БД и не логируются. Псевдоним нужен для разных сигналов и доступа к собственным обращениям; исходный ID также проверяется по списку администраторов, но не выдаётся клиенту. Администратор видит агрегированные инциденты, а не чужие описания.

Сессия хранится в памяти сервера, в браузере — только случайный HttpOnly cookie (Secure в production). После рестарта backend или истечения сессии нужно заново открыть приложение из MAX. Запросы изменения данных требуют ожидаемый origin и специальный заголовок; публичного CORS нет. Текст описания выводится экранированным.

**Настоящие заявки не хранятся в localStorage.** Соседи получают только категорию выбранного места, количество, время и статус. В форме нет ФИО, телефона, квартиры/комнаты или фото; есть предупреждение не вводить личные данные. Самостоятельно введённое описание остаётся на сервере и у автора.

## 7. Правила и ограничения MVP

- Пилот ИТМО: три разных пользователя, совпадение дома, категории проблемы и выбранного места за 20 минут включительно. Повторы не увеличивают число разных участников.
- Создание заявки и инцидента выполняется в сериализованной транзакции SQLite. Повтор с тем же `requestId` не создаёт дубль. В режиме ИТМО возможны разные временные группы с одинаковой категорией места; каждая содержит обращения в пределах 20 минут.
- В режиме ИТМО новый сигнал присоединяется только если все обращения группы укладываются в 20 минут; иначе начинает новую волну. Исторический режим физических зон в отдельном демо сохраняет прежнее поведение. Счётчик показывает реальные отправки, не заселённость общежития.
- Статусы: «Проверяется», «Мастер вызван», «Устранено». Устранённый инцидент остаётся в истории и не открывается повторно. Для новой волны нужны три новых подходящих сообщения.
- Нет инженерной диагностики, контакта с реальной УК, автоматических уведомлений ей или фактического вызова мастера. Статус меняет администратор.
- Привязки аккаунта к праву проживания пока нет: участник с подтверждённым входом бота может выбирать настроенные дома пилота. Для ограниченного набора участников распространите доступ к боту в рамках согласованного пилота; это не проверка проживания.
- Один backend и один постоянный диск. Сессии и короткая защита от повторных webhook-событий — в памяти; доставка ответов бота не имеет гарантии exactly-once при перезапуске процесса.
- Настройку TLS, запуск в реальном MAX, доступность сторонних cookie в конкретном web-клиенте и права вашей учётной записи нужно проверить на реальном размещении. С выданным токеном на реальном HTTPS-хостинге это ещё не проверено.

## 8. Тесты, сборка и структура

```sh
npm test
npm run build
```

Тесты проверяют оба режима: порог и повторы, разные зоны, границу 20 минут, отсутствие дублей, новую волну после устранения, изоляцию демо, повтор запроса, приватность API, сохранение SQLite, HMAC и просроченный вход, запрет production-обхода, права администратора, CSRF, закрытые служебные файлы и сообщения бота без обращения в реальный MAX.

Сборка проверяет синтаксис JS и создаёт **безопасный статический preview** `dist/public`. Backend не требует компиляции; для живого пилота запускается исходный Node-сервер. Preview без backend покажет, что отправка недоступна.

GitHub Pages workflow запускается вручную через Actions → Deploy prototype to GitHub Pages → Run workflow после настройки Pages в репозитории. Он публикует **только** `dist/public`, а не корень репозитория. `.env`, базы, backend и административное демо туда не копируются. GitHub Pages не заменяет сервер пилота. Отправка коммитов сама по себе не публикует сайт.

- `index.html`, `pilot.js`, `pilot.css`, `bridge.js` — серверный пилот и MAX Bridge.
- `styles.css`, `demo.css` — сохранённый стиль прототипа и адаптация.
- `demo.html`, `app.js`, `model.js` — автономное изолированное демо.
- `server/` — HTTP API, проверка MAX, сессии, конфигурация, SQLite.
- `bot/` — обработчик старта и ручная регистрация webhook.
- `config/` — данные домов и настроенных зон.
- `tests/` — тесты встроенным Node test runner.
- `.env.example` — образец настроек без секретов.
